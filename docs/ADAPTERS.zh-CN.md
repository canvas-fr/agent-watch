# Agent Watch 适配器与事件协议草案

> 此文件保留早期设计草案。0.2.0 实际事件字段以 EVENTS.md 和 schemas/event.schema.json 为准；草案的 app/entity_id 字段不应直接用于发送事件。

> 本文描述后续阶段的 proposed（提议中）协议和测试方案，不是已实现接口，也不是目标应用适配完成证明。第 0 阶段不读取聊天正文或截图，不激活应用；本表中的适配测试尚待逐项执行。

## 统一事件草案

适配器应尽量产生可审计的状态观察事件。每个字段是否可得、从何处观察，均需记录；拿不到的信息留空或标未知，不得推断。

| 字段 | 含义 |
| --- | --- |
| protocol_version | 协议草案版本 |
| event_id | 事件唯一标识；用于重复事件识别 |
| app、mode | 应用与模式，例如 Claude 的 Chat、Cowork、Code |
| entity_id、entity_role | 被观察实体及其角色：parent 或 subagent |
| parent_entity_id | 子代理所属 parent；parent 自身留空 |
| turn_id | 当前轮次标识；无法取得时留空 |
| status | 运行、等授权、等回答、本轮结束、失败、取消、未知之一 |
| source | 状态来源及具体观察类型 |
| observed_at、received_at | 观察发生时间与 Agent Watch 收到时间 |
| freshness | 新鲜、陈旧或未知，并保留判定依据 |
| detail | 非敏感的简短原因码或说明；不得包含聊天正文 |

状态来自适配器的观察，不等同于应用内部的权威状态。“本轮结束”只结束对应 turn；parent 和各 subagent 状态分别维护。应用级安装/进程元数据不能直接生成任务完成或失败事件。

## 状态判定约束

- **运行**：只有存在与目标实体相关的新鲜活动信号时才报告。
- **等授权**：需要用户批准/授权的信号可明确识别时报告；否则为未知。
- **等回答**：明确观察到应用正在等待用户回答问题时报告；不能把模型生成响应的等待时间或进程空闲解释成等待用户。
- **本轮结束**：有本轮结束信号时报告，并保留轮次标识；不自动结束 parent。
- **失败 / 取消**：需有明确失败或取消信号；窗口关闭或进程退出不足以单独证明。
- **未知**：信号缺失、权限不足、观察过期或来源冲突时使用。

来源和新鲜度始终随状态展示。陈旧的“运行”不能继续作为当前正在运行的证据；连接中断时保留最后观察并将其标为陈旧，恢复后重新核对。

## 升级、去重、乱序与断线

1. **去重**：优先按 event_id 去重；同一事件重发不得重复计数。没有稳定事件标识时，只能按适配器明确提供的实体、轮次、状态和观察时间做保守去重，且不得合并 parent 与 subagent。
2. **更新/升级**：仅用同一实体、同一轮次内较新且来源可比较的观察更新当前状态。轮次改变后可以从终态进入新一轮状态，但须保留轮次边界和历史。
3. **乱序**：优先用同一来源的序号或修订信息判断先后；不单凭不同来源的墙钟时间覆盖状态。旧事件不得覆盖更新的状态。若无法确定顺序，保留事件并将当前状态标为冲突/未知，等待重新观察。
4. **断线**：断线不等于失败、取消或完成。保留最后状态及时间并标为陈旧；恢复后先重新读取当前可用信号，再继续更新。
5. **父子关系**：subagent 的完成、失败或取消只更新该 subagent。parent 需有自己的状态证据；不得从子代理事件推导 parent 已结束。
6. **无证据状态**：不以应用关闭、AX 元素消失、窗口切换或进程退出单独推断任务终态。

具体超时阈值、来源优先级和应用内状态映射应在取得实测证据后确定，不在本草案中预设。

每行均需分别做前台、后台和多窗口观察。这里的“后台”指应用不在前台时进行只读观察，不得为了观察而激活应用。若应用不支持多窗口或无法区分独立实体，记录“不支持/未知”和证据，不得伪造通过。当前全部待测。

| Antigravity | 活动任务与状态信号是否对应 | 后台活动能否被动观察且标新鲜度 | 两个独立任务是否区分 | 待测 |
